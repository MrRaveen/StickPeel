## 1. Starting point and environment
- Start from the Launchbase repo: `git clone https://github.com/chamoda/launchbase your-product-name`
- Follow the root `README.md` and each folder's `README.md`
- Monorepo with 4 folders:
  - `api/`: FastAPI, async SQLAlchemy, Postgres, Alembic, JWT auth, users, pytest. It has two surfaces: `/app` and `/internal`
  - `app/`: customer app (TanStack Start) with login, an auth-guarded sidebar layout and a typed API client generated with orval
  - `internal/`: staff console (TanStack Start) with user management on the `/internal` surface
  - `site/`: statically generated marketing site (TanStack Start) with a placeholder page and the full shadcn/ui set
- Use Linux or macOS. On Windows use WSL 2 with Ubuntu, and keep the repo under `~/`, not `/mnt/c`
- Required tools: Python 3.12 with uv, Node.js 24+, Postgres 16, Docker (the tests use it to start their own Postgres)

## 2. Conventions from Launchbase's AGENTS.md
- Use `uv run` for everything in Python
- Alembic migrations are autogenerated
- No enums in models
- Services flush, routers commit
- New resources should look like the existing users resource
- Use the typed client and regenerate it with `npm run generate`. No hand-written fetch calls
- If the brief and an AGENTS.md disagree, the brief wins. Example: tests are required here

## 3. Backend features
- Sign-up with email and password only
- A new user creates an organization or joins one through an invite. A copyable invite link is enough, with no email sending
- Org roles: owner, admin, member
- Teams inside an org, with members and a lead. A user can be in more than one team
- Plans keyed by the week's Monday date: one main task, sub-goals and go-to-market goals
- Each task has its own status
- Plan status flow: draft → submitted → approved → done
- The lead approves or sends back with a comment
- The member marks whether the main task shipped
- Team week view for the lead, and a history view of past weeks
- Org plans table, teams, plans and members are all new tables with Alembic migrations
- `manage.py` seed command: at least 2 orgs, a few teams, members in every role, several weeks of plans (some shipped, some not)

## 4. Security and tenancy (highest weight)
- Everything is enforced in the API, not by hiding buttons
- Reviewers will send requests with someone else's IDs, so every ID must be checked
- A user in one org must never read or change another org's data
- A member must not be able to act as an admin
- A non-lead must not be able to approve a plan
- Customer owners and admins must not reach the `/internal` surface
- Staff use the existing `is_admin` flag, granted with `uv run manage.py create-user --admin`
- Tokens are scoped to the internal surface
- Staff are never created through sign-up
- Keep `is_admin` (platform staff) clearly different from the org admin role in the code
- A suspended org locks its members out until it is reinstated
- A deactivated account cannot use the product

## 5. Internal admin panel (`internal/` + `/internal` API)
- Organizations list: member count, team count, plan count, last active
- Suspend and reinstate an org
- Users: search, see which orgs a user belongs to, deactivate an account
- AI usage: calls per org, failures, rate-limited calls
- Clearly marked as internal
- Make a deliberate decision about whether staff see plan text, and be ready to explain it

## 6. AI integration
- Use Pydantic AI with Google's Gemini model `gemini-3.5-flash-lite`
- Install: `cd api && uv add "pydantic-ai-slim[google]"`
- Free API key from Google AI Studio, stored as `GOOGLE_API_KEY=...` in `api/.env`
- Add an empty `GOOGLE_API_KEY=` to `api/.env.example`
- The key is read through the API settings, stays on the server, never reaches the browser and is never committed
- Both features use a Pydantic model as the agent's `output_type`. Don't ask for JSON in the prompt and parse a string
- **Plan review:**
  - Returns a structured review
  - Flags tasks that describe work instead of a checkable result, a main task without why it matters, missing go-to-market goals, and scope too big for one week
  - Each finding points at a specific task with a suggested rewrite
  - The UI shows findings next to their tasks and the member can apply a suggestion with one click
- **Draft from a brain dump:**
  - Pasted notes become a pre-filled plan in the form
  - The output goes into the form and never straight into the database
- The product must work without the AI. If Gemini is slow, down or returns 429, planning still works, the UI says what happened in plain words, and nothing hangs or crashes
- Don't fire a request on every keystroke
- Record every call against the organization that made it, with whether it succeeded. This feeds the admin usage view
- Show a loading state while the model thinks
- The AI must do real work. If a textarea could replace it, the feature fails

## 7. Testing
- Tests are required
- Tests must not call Gemini. Use `TestModel` or `FunctionModel` from Pydantic AI
- `uv run pytest` must pass with no key and no network access to Google
- Cover the agent code and the tenancy rules, not only CRUD
- Docker is needed because the test suite starts its own Postgres

## 8. Frontend (all three apps)
- Loading states, clear empty states, forbidden pages that say so, and no dead buttons
- Use the generated typed client
- Replace Launchbase in: page `<title>`, favicon, header, sign-in and sign-up screens, landing page, admin panel
- Nothing user-facing may still say "Launchbase"

## 9. Brand and landing page (`site/`)
- Brand name: short, easy to say and spell, not an obvious known product in the same space
- One-line pitch, and a sentence on why you chose the name
- Logo as SVG, used as favicon, in the app header, on the sign-in page and on the landing page
- The logo must read at 16px and work on light and dark backgrounds
- Render the logo at 16px, 32px and large, check it, and iterate
- Landing page sections:
  - Hero with name, logo, one sharp line, and a Get started button leading to sign-up in `app/`
  - How it works
  - Show the AI, with a rendered example of a review that flags a vague task and suggests a rewrite (not a stock illustration)
  - For teams
- Responsive down to a phone
- Proper `<title>` and meta description
- Open Graph image
- No lorem ipsum

## 10. How to build it
- Use a full agentic coding tool (Claude Code, Codex CLI, OpenCode or similar). Autocomplete tools aren't enough
- Plan first: have the agent propose the data model and tenancy rules, review, then build
- Give the agent ways to check itself: tests, seed script, dev server
- Add a `CLAUDE.md` that contains `@AGENTS.md`
- Update `AGENTS.md` whenever the agent makes a mistake
- Review everything the agent writes
- Commit in small steps

## 11. Delivery
- `SUBMISSION.md` at the repo root with:
  - How to run it, the seed command, and demo logins for a member, a team lead, an org owner and a staff user
  - Brand name, one-line pitch, and why you chose the name
  - Your real hours
  - What isn't done, what you cut, and what you'd fix with another day
- Commit everything:
  - `git add -A`
  - `git commit -m "Final submission"`
  - `git archive --format=zip -o assessment.zip HEAD`
- Don't zip the project folder directly
- `git archive` leaves out `node_modules`, `.venv` and `api/.env`, so the key stays out
- Unzip into a fresh folder and check it runs from your instructions before uploading
